Design proposal · for approval

omega-ai Game Studio

A Claude Code plugin that turns claude-gd into a small game studio: eight stage skills you drive by hand, ten role agents that run long sessions, and a toolkit that can build, test and boot a Godot project. Composed from superpowers (process) and gstack (roles, hand-offs) — adjusted for how games actually get made.

2 · What we took, what we changed

The two reference frameworks answer different questions. superpowers answers how to work; gstack answers who does the work and what they hand each other. Neither knows what a playtest is.

From superpowers

Take
  • Skill-first discipline: check for a skill before any action
  • Brainstorm gate — no code before an approved design
  • Spec → plan → fresh subagent per task → reviewer per task
  • Red/green TDD, verification-before-completion, git worktrees
  • Writing skills as TDD on documentation
Change
  • TDD is mandatory only for tasks tagged Verify: unit. Feel, animation and layout tasks get playtest criteria instead — a unit test cannot tell you a dash feels floaty.
  • Brainstorm gains GDD-lite sections: core-loop delta, player verbs, feel targets, not-doing list.
  • A playtest stage exists at all.

From gstack

Take
  • Named specialists with a persona and an output contract
  • Each stage writes a file the next stage reads
  • Decision-brief format for every approval question (stakes, recommendation, options)
  • QA loop: find → fix → regression test → re-verify
  • Router skill, retro and learnings that compound
Change
  • CEO "think bigger" becomes producer "cut to the vertical slice". Games die of scope, not of timidity.
  • Browser QA becomes headless Godot runs plus a human playtest script.
  • Dropped: Bun binaries, browser daemon, telemetry, design-html, security audit. Nothing to compile, nothing phoning home.

From the industry

Baked in
  • Vertical slice before content; milestone gates prototype → vertical slice → alpha → beta → gold tracked in PROGRESS.md
  • GDD-lite as a living decision log, not a 40-page dream
  • Playtests state a hypothesis first ("expected perceptual change"), then measure
  • Feel targets in real units: input latency ≤ 2 frames at 60 fps, coyote time ≈ 0.1 s, frame budget 16.6 ms
  • Data-driven tuning: numbers live in Resource files a designer edits without a programmer
  • Import settings and project settings are code — versioned and reviewed

3 · Setup: how the studio reaches a session

One command installs a studio. The config directory holds only what Claude Code must own (settings, rendered instructions, memory, plugin cache). Skills, agents, hooks and tools stay in the repo and load live through --plugin-dir, so an edit to a skill is active in the next session with no reinstall.

4 · Workflow: the studio sprint

Every stage is a skill you can call by name. Each one reads the file the previous stage wrote and writes one of its own, so a stage can be re-run, skipped when it does not apply, or picked up in a new session. Three points require your explicit approval — marked in amber.

Stage skillWhat it doesReadsWritesDelegates to
/game-dev:studioRouter. Reads state, names the next stage, routes freeform text ("add a dash" → brainstorm; "it feels floaty" → playtest). Shows milestone.STATE.md——
/game-dev:brainstormBatched clarifying questions, spike/bounded/architectural classification, 2–3 approaches, spec with GDD-lite sections and a test strategy (which behaviour gets unit tests, which gets playtest criteria). Renders spec as an Artifact page; waits for approval.GDD, PROGRESS.mddocs/game-dev/specs/, artifact exportgame-dev:gdd, core-loop, game-feel

/game-dev:executeSubagent-driven: fresh role agent per task with only the task and the spec excerpt it needs; TDD when Verify: unit; reviewer agent after each task; ledger of rulings. --inline switches to checkpointed inline execution.plan.mdcommits, ledger in STATE.mdrole agents; superpowers TDD, worktrees, debugging
/game-dev:reviewWhole-branch review by the reviewer agent: spec compliance, Godot anti-patterns (inheritance chains, cross-system references, magic numbers outside Resources), performance smells. Fix loop.spec, diffreview notes, fix commitsgodot-prompter:godot-code-review
/game-dev:playtestRuns studio-test (GUT headless) and studio-run (boots the scene, captures errors). /game-dev:scaffoldNew Godot 2D project from engines/godot/template: folder layout, EventBus autoload, GUT installed, .studio/, docs/game-dev/, project CLAUDE.md, gdlint config.—project treegodot-prompter:godot-project-setup
Precedence rule (injected by the session hook): game-dev:* stage skills own the workflow. superpowers skills run only when a stage skill names them. godot-prompter skills run inside role agents for engine work. If superpowers' own bootstrap says "invoke brainstorming", invoke game-dev:brainstorm instead.

6 · Roles: the ten agents

Agents are the long-session workforce. A stage skill dispatches them with a fresh context and exactly the task in hand; they never inherit your conversation. Each has a persona, the skills it may call, and an output contract — the file or commit it must leave behind.

AgentOwnsDispatched byOutput contract
game-dev:game-designerCore loop, mechanics, progression, GDD-lite. Engine-agnostic. Never opens engine files.brainstorm (design pass)GDD sections in the spec
game-dev:level-designerLevel layout, pacing, teaching sequence, tile rules.brainstorm, executelevel spec, TileMap authoring notes
game-dev:architectScene tree, state machines, signal/event-bus topology, Resource schemas.brainstorm (architectural path), planarchitecture section, task decomposition
game-dev:gameplay-programmerImplements tasks in GDScript with TDD. Calls godot-prompter skills for engine patterns.executecommits + passing tests
game-dev:tech-artistSprite pipeline, atlases, import settings, pixels-per-unit, animation frame budgets.executeassets + versioned import settings

game-dev:ui-designerControl-tree HUD and menus, themes, responsive layout.executeUI scenes + theme resource

The existing three agents (game-designer, 2d-art-pipeline, game-feel-tuner) and four skills migrate into this set with their content kept.

7 · Toolkits

bin/ — verbs the skills call, never the engine directly

CommandDoesGodot adapter
studio-test [path]Run the project's test suite headless; exit non-zero on failure; JUnit XML for the ledger.godot --headless -s addons/gut/gut_cmdln.gd -gexit
studio-run [--scene S] [--seconds N]Boot the project or one scene for N seconds, capture stdout/stderr, fail on script errors.godot --headless --quit-after / windowed with timeout
studio-lintgdlint + gdformat check when installed; clear install hint when not.gdtoolkit (pip)
studio-state get|set KEY [VALUE]Read/write .studio/STATE.md fields so every skill updates state the same way.—
studio-scaffold DIRMaterialise engines/godot/template into a new project.template copy + GUT addon

Engine resolution order: $GODOT_PATH → /Applications/Godot*.app/Contents/MacOS/Godot → godot on PATH. Your machine resolves to Godot_mono.app.

Hooks

One SessionStart hook, modelled on superpowers'. It injects hooks/bootstrap.md: the studio identity line, the precedence rule, the stage list, and "read .studio/STATE.md if present". No PreToolUse or PostToolUse hooks — nothing runs on every tool call.

MCP (optional)

godot-mcp (Coding-Solo, MIT) gives the session: launch editor, run project with debug output capture, create scenes and nodes, UID maintenance. It needs Node ≥ 18. The installer registers it at user scope inside the studio's config directory (claude mcp add godot -- npx -y @coding-solo/godot-mcp with GODOT_PATH set) only when Node is present; --no-mcp skips it. It is deliberately not in the plugin's .mcp.json, so a machine without Node never sees a startup failure.

Scaffold

engines/godot/template is a runnable Godot 4 2D project: src/ by feature, autoloads/EventBus.gd, resources/tuning/, tests/unit/ with GUT, project.godot with base resolution and stretch mode set, nearest-neighbour filtering, a project CLAUDE.md carrying the studio standards, .studio/config.json, docs/game-dev/, .gitignore, .gdlintrc.

8 · Extensibility seams

Godot 2D GDScript is the first pack, not the design. Three seams keep 3D, another language, or another engine from being a rewrite.

# per-project .studio/config.json
{ "engine": "godot4", "dimension": "2d", "language": "gdscript", "tests": "gut" }

# per-studio studios/game-dev/engines/<engine>/
GUIDE.md        # which external skills to call for this engine (godot → godot-prompter:*)
resolve.sh      # find the engine binary
test.sh run.sh lint.sh   # the studio-* verbs dispatch here by config.engine
template/       # scaffold source
  • Dimension. Domain skills carry a 2D section now; a 3D section is added to the same skill (camera, lighting, mesh pipeline). config.dimension tells the skill which to read. New 3D-only skills get a 3d- prefix.
  • Language. config.language routes the gameplay-programmer to godot-prompter:godot-csharp-engineer and the test verb to gdUnit4. The stage skills never mention a language.
  • Engine. A Unity pack is engines/unity/ with the same four files plus a GUIDE naming the Unity skills. Stage skills, roles, state and docs layout do not change.
  • Another studio. studios/<name>/ with its own studio.json; the installer has no per-studio branches.

9 · State, docs and memory

  • State lives in the game project: .studio/STATE.md with stage, spec, plan, task, last_playtest, and the execute ledger. Every stage updates it through studio-state; the router reads it; a new session resumes from it. That is the whole of what we borrow from GSD.
  • Docs follow one layout in both places. This repo: docs/game-dev/{specs,plans,artifacts,PROGRESS.md} tracks the studio's own evolution — this page is its first artifact. A game project: docs/game-dev/{specs,plans,playtests,artifacts} plus PROGRESS.md with the milestone gate.
  • Memory is isolated by construction: the game studio's memory directory is ~/.claude-gamedev/memory/, a different config root from any other studio. sync-memory.sh game-dev copies only into studios/game-dev/memory/. The retro skill is the one writer.

10 · Testing the framework itself

The existing POSIX shell harness in tests/ stays and grows. No Bun, no Node required to test.

  • Install into a temp target: rendered CLAUDE.md, copied settings, linked memory and bin, shim contains --plugin-dir and the PATH prefix; uninstall leaves nothing.
  • Plugin manifest is valid JSON with name: game-dev; every skills/*/SKILL.md and agents/*.md has frontmatter whose name matches its directory and a description that starts with "Use when".
  • Doctor fails when a delegated skill name (superpowers:…, godot-prompter:…) is not present in the plugin cache.
  • All bin/ and engines/*/ scripts pass sh -n; studio-scaffold into a temp dir produces the expected tree; studio-test against the template runs when Godot is found and reports "skipped: no Godot" otherwise.
  • Skill behaviour is verified the superpowers way: a pressure scenario run without the skill (baseline), then with it — documented per skill in docs/game-dev/.

11 · Delivery in three plans

One design spec, three sequenced implementation plans. Each plan ends with a working claude-gd.

1

Foundation. profiles/ → studios/, plugin packaging, shim with --plugin-dir and PATH, installer / uninstaller / doctor / tests updated, session hook, docs/game-dev/, .studio/STATE.md + studio-state, and the four skills your daily loop needs: studio, brainstorm, plan, execute.

Exit: plan and execute a feature in an existing Godot project through claude-gd.

2

Quality loop. Ten role agents, review, playtest, ship, retro, bin/ verbs with the Godot adapter, optional godot-mcp registration, doctor delegation check.

Exit: the full session in §5 runs end to end.

3

Content. scaffold + template project, migrate the four existing skills and add vertical-slice, tuning-data, milestone-gates; PROGRESS.md conventions; general studio parity; skill pressure tests.

Exit: a new game project from zero to first playtest using only studio commands.
